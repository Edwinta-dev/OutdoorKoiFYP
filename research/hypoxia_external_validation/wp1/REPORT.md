## 2. Findings (production behaviour; nothing fixed, per instructions)
Reproducers: `reproducers.py` (output `out/reproducers_output.txt`) and the SYN tests named below.
- **F1 low. `WaterChemistryEngine.from_snapshot` prunes day buckets against the wall clock** (`_prune_daily(datetime.now())`). A Jan-2026 snapshot loaded on 2026-10-22 keeps 0 of 3 buckets. Harmless when data time is near wall time; it makes restore/replay of historical data clock-dependent (hence `frozen_clock`, assumption A10). Test `snapshot_from_snapshot_prunes_daily_against_wall_clock_F1`.
- **F2 medium (relevant at the design cadence). SensorGate rate check latches.** The limit is `max_rate x hours since the previous SAMPLE`, but the comparison is with the last TRUSTED value, which updates only on `ok`. After one genuine step larger than the limit (pH 7.02 to 7.60, limit 0.25 per 15 min) with no logged water change, all 288 readings of the next 3 days are `suspect_rate`; with a logged event within 6 h none are. Real data: Oman tank 5-min grid, pH latch 79 h and 32 % pH `ok` without events vs 91 % with the 4 logged water changes; IDN-T thinned to 15 min, pH latch 99 h; FWI pond 3ed4df8e 35.7 h. Cadence effect (F2b): at 1-min spacing the limit is 0.0167 pH, so noise of sd 0.03 gives 30 % ok (99.8 % at 15 min); native Oman 6 s pH ok 0.05 %, IDN-T 1-min raw pH ok 1.4 %. F2b is a cadence mismatch, not a defect at 15 min; F2 is. Bounded consequence: `sensor_channels` keeps the raw newest value whatever the verdict; the gate feeds chemistry day aggregates and warnings. Tests `gate_rate_limit_latches_...`, `gate_rate_limit_scales_with_dt_...`; table S4-H.
- **F3 low. out_of_window rows can be re-applied.** `sensor_ingest_history` (migration 0029) does not filter by disposition. SYN reproducer (45 days; 12 inputs ledgered `out_of_window` on arrival): an event logged just after the retained pre-window checkpoint starts a replay that reads all 12 back and applies them, contrary to the recorded disposition. Test `ledger_out_of_window_rows_can_be_reapplied_by_a_later_replay_F3`. Confined to the 30-day edge.
- **F4 low-medium. `TdsPrompts.observe` depends on arrival order.** It skips any reading with `time <= last_reading_at`. (a) A late reading never enters the baseline (SYN: 4 late readings change the state). (b) If the rows of one sample instant arrive in two polls it keeps the first row, while `sensor_inputs`/`PondTwin` use the highest row id (SYN: prompt state 300 ppm, twin channel 400 ppm). On IDN-T (several rows per minute) one chunk of delay moves a prompt by 20 min and its level 435.5 to 439 ppm; shuffled chunk order gives 2 prompts instead of 4 (cleaned, 15-min). Tests `tds_prompts_late_reading_...`, `..._F4b`; table S3-E.
- **F5 info. Stale rule vs resolution.** 17 % of FWI pH and 23 % of FWI temperature inputs are `suspect_stale` (4 identical values). In 98.9 % (pH) and 98.8 % (temp) of stale episodes the independent DO column of the same monitor kept moving (DO used as a label only, never fed), so these are resolution repeats, not frozen devices (S4-K). Since stale flags lower confidence to `reduced`, a hypothesis is false "probe may be stuck" notices on 0.1 C probes (ESP32 nodes may differ; untested).
- **Positive checks.** README zero artefacts: pH=0 rejected 516/516; temp=0 never `ok` (86 stale + 7 rate; 0 C is inside the [-5,45] range, so a zeroed probe is caught only by rate/stale). No future event ever in the ledger (10 Oman events, checked batch by batch). Duplicate event ids are no-ops; edit, delete and restore equal an in-order oracle; events older than the window are `placed_late` as documented.
