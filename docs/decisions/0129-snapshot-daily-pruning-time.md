Status: implemented · Issue: #129 · Date: 2026-10-23

## In short
`WaterChemistryEngine.from_snapshot` now determines daily retention from the newest calendar day stored in that snapshot. Loading the same historical snapshot therefore retains the same buckets regardless of the machine's current date.

## How it works
1. The loader reconstructs the snapshot's daily aggregates, including legacy buckets.
2. If buckets exist, it finds the newest calendar date represented by them using the pond's configured time zone.
3. It constructs a reference instant at midnight on that date in the same time zone, then applies the existing rolling retention rule.
4. The loader continues restoring the remaining chemistry and sensor-gate state as before. An empty daily collection needs no pruning.

## Main design choice
Use the snapshot's newest daily bucket as the retention reference. The alternative was to add a `now` parameter with a wall-clock default. That would make deterministic replay possible only for callers that remember to pass the parameter, while existing callers would remain time-dependent. The bucket is already the source data whose retention is being evaluated, so it gives replay and ordinary snapshot loading the same behavior without changing the API. An explicit reference would be better if callers later need to prune a snapshot to a separately chosen replay cutoff.

## Traps: why the obvious fix is wrong
- Keeping the existing wall-clock reference discards valid old buckets during historical replay or rebuild; #129's January 2026 snapshot is affected when loaded months later.
- Selecting the maximum serialized key is unsafe for legacy keys, whose format is not zero-padded. Compare `DailyAggregate.calendar_date()` values instead.
- Do not change `_prune_daily`'s retention boundary: live ingestion and snapshot loading share that policy, and this issue changes only the reference time.

## Components
- `Backend/koi/models/engine.py::WaterChemistryEngine.from_snapshot` — snapshot-time reference.
- `Backend/koi/models/engine.py::WaterChemistryEngine._prune_daily` — existing retention policy.
- `Backend/tests/models/test_new_engines.py::test_chemistry_snapshot_daily_retention_uses_snapshot_data_time` — wall-clock independence regression.

## Breaks or needs follow-up
None.

## Problem and constraints
The previous load path pruned historical data against the current UTC instant. The fix is scoped to the chemistry engine, its model test, and this record; snapshot shape and live ingestion are unchanged.

## Alternatives considered
- Pass an explicit time argument to `from_snapshot` — adds caller responsibility and leaves default loads nondeterministic.
- Skip pruning on load — avoids data loss but stops self-healing oversized old snapshots.

## Trade-offs
If a snapshot contains a stale daily bucket later than all its actual data, that bucket sets the reference and can preserve older buckets within the existing retention window. The snapshot's daily data is treated as its time authority.

## Key parameters
- Retention remains 30 calendar days (`Backend/koi/models/engine.py::WaterChemistryEngine.DAILY_RETENTION_DAYS`); this issue does not change the configured window.

## Assumptions
The latest daily aggregate date represents the snapshot's latest daily data time. If snapshots later include an explicit replay timestamp, that could provide a more precise authority.

## Edge cases
- Handled: empty daily collections skip pruning; legacy aggregates use their `calendar_date()` values; pond time zones are used for the reference midnight.
- Not handled: a malformed daily aggregate cannot be loaded; snapshot parsing already fails before pruning.

## Not verified
No separate measurement was made for very large historical snapshots.

## To change this
To make retention relative to an externally supplied replay cutoff, add an explicit cutoff parameter to `from_snapshot` and update its callers; this makes the selected replay time caller-owned.

## Rollback
Reverting `WaterChemistryEngine.from_snapshot` restores wall-clock-dependent pruning. Check historical snapshot reloads and replay/rebuild results if reverted.
