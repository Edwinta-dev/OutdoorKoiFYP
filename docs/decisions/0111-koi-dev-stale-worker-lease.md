Status: implemented · Issue: #111 · Date: 2026-10-19

## In short

The local Supabase seed now removes the poller lease before replacing demo data. A worker started after an unclean stop can acquire the lease immediately instead of waiting for the old lease to expire.

## How it works

1. koi.dev connects to the local Supabase database before it starts the API, camera service, or worker.
2. The seed transaction removes the existing poller lease, then performs its normal demo row cleanup and insert.
3. After seeding finishes, the worker starts and claims the poller lease for its own process.
4. A regression test checks that the seed issues a deletion for the poller lease before any other seed cleanup.

## Main design choice

Clear the lease through the existing direct database connection during the seed. This uses the fact that the local dev seed owns the disposable local database. Asking the storage adapter to release it is not viable because the abandoned holder belongs to a previous process and the adapter only releases a lease for the supplied holder. Letting the existing lease expire would preserve ownership semantics but leaves a newly started local stack idle until expiry.

## Traps: why the obvious fix is wrong

- Releasing the lease from the new worker cannot work: the persisted holder belongs to the stopped process, so holder-checked release is a no-op.
- Deleting leases outside the local seed would weaken normal worker coordination for non-dev profiles. The cleanup stays at the local database boundary.

## Components

- `Backend/koi/dev/local_db.py::seed` — clears local poller lease
- `Backend/koi/dev/local_db.py::POLLER_LEASE` — lease key
- `Backend/tests/dev/test_dev_stack.py::test_supabase_seed_clears_stale_poller_lease_before_replacing_seed` — regression coverage

## Breaks or needs follow-up

None. The local dev seed intentionally takes over the poller lease on each invocation.

## Problem and constraints

An uncleanly stopped koi.dev process leaves the poller lease row until its TTL expires. A restart can therefore put its worker on standby. The issue is limited to the local Supabase development profile.

## Alternatives considered

- Wait for lease expiry — leaves the local worker unavailable during that interval.
- Add a force-takeover operation to the shared storage contract — broadens behavior beyond the local dev seed and affects both storage implementations.

## Trade-offs

Seeding while another local koi.dev instance is still running removes its lease; that instance may continue operating without the poller lock. This is acceptable for an explicitly invoked local seed that owns the disposable database.

## Key parameters

None added.

## Assumptions

The local Supabase seed is an intentional owner of this local development database. If multiple independent workers are meant to share it while reseeding, forced lease removal could allow concurrent polling.

## Edge cases

- Handled: a stale poller lease row is removed before the replacement worker starts.
- Not handled: concurrent active koi.dev instances during a reseed; the seed takes over the shared local lease.

## Not verified

The local Supabase seed against a running database was not run here.

## To change this

To preserve leases across reseeds, remove the deletion in `Backend/koi/dev/local_db.py::seed`; cost: an uncleanly stopped worker can keep a subsequent local stack on standby until its lease expires.

## Rollback

Remove the lease deletion and its test. Restarts after hard stops will again rely on normal lease expiry.
